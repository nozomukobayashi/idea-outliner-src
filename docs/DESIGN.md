# Idea Outliner 設計書

GitHub / GitHub Enterprise Server (GHES) の Discussions と Issues を土台にした、チームで共有できるアウトライナー。
アイディアやメモをアウトラインで書き溜め、良いものを Issue に昇格させ、議論は Discussion のコメントで行う。

- ステータス: M0〜M5 完了。M1〜M4 は github.com の実データで確認済み。§9 の確認項目は社内 GHES でもすべて OK（結果: `docs/spike/M0-results.md`）。GHE Pages への手動デプロイで動作確認済み、Actions でのデプロイは未確認
- 対象: github.com と GHES 3.20 以降（社内 GHE で確認済み）

---

## 1. 目的とスコープ

### やりたいこと
- アイディア・メモをアウトライン形式で素早く書ける
- チームで同じノートを見て、行単位で議論できる
- 行を Issue に昇格でき、Issue の状態（Open / Closed）がアウトライン上に見える
- GHE だけでなく github.com でも使え、外部にも配布できる

### やらないこと（少なくとも v1 では）
- 独自サーバー・独自データベース（データはすべて GitHub 上に置く）
- リアルタイム共同編集（同時編集は「上書き前に検知して知らせる」まで）
- 独自のユーザー管理・共有設定（権限はリポジトリの権限に任せる）

---

## 2. 全体構成

```
┌──────────────────────────┐
│ アプリ（静的サイト）      │  GitHub Pages / GHE Pages で配信
│  HTML + JS のみ           │  データは持たない
└────────────┬─────────────┘
             │ ブラウザから直接 API（各自のトークン）
             ▼
┌──────────────────────────┐      ┌──────────────────────────┐
│ アイディア用リポジトリ     │      │ プロジェクトのリポジトリ群 │
│  例: team-a/ideas         │      │  例: team-a/api, team-a/web │
│  Discussions = ノート     │ ───▶ │  Issues = 昇格したアイディア │
│  カテゴリ = プロジェクト   │ 参照 │                          │
└──────────────────────────┘      └──────────────────────────┘
```

- **アプリ**: 静的ファイルのみ。誰でも自分の Pages にホストできる。サーバー処理なし。
- **アイディア用リポジトリ**: チームごとに 1 つ。Discussions を有効化し、カテゴリでプロジェクトやテーマを分ける。社内では internal 公開を推奨。
- **プロジェクトのリポジトリ**: Issue 化の行き先。1 つのノートから複数リポジトリへ Issue を作れる。

### 共有の考え方
アプリ側に共有機能はない。「アイディア用リポジトリを見られる人」がそのままノートの閲覧者になる。
アプリを使わない人も GitHub の Discussions 画面から読んでコメントできる。

## 3. 接続と認証

### 接続先の設定
ユーザーが「接続」を複数登録でき、切り替えて使う。

| 項目 | github.com | GHES |
|---|---|---|
| 表示名 | GitHub | 任意（例: 社内 GHE） |
| REST ベース URL | `https://api.github.com` | `https://<host>/api/v3` |
| GraphQL URL | `https://api.github.com/graphql` | `https://<host>/api/graphql` |
| Web URL（リンク生成用） | `https://github.com` | `https://<host>` |

ユーザーはホスト名だけ入力し、URL はアプリが組み立てる。

配布時は、ビルド時の設定（`config.json` など）で既定の接続先を埋め込めるようにする。
社内配布版は社内 GHE を既定に、公開版は github.com を既定にする。

### 認証（v1）
- Personal Access Token（PAT）を各ユーザーが入力する
- 既定ではタブの間だけ保持する（sessionStorage）。再読み込みでは消えず、タブを閉じると消える。ユーザーが「このブラウザに保存する」を選んだときだけ localStorage に保存する。どこにも送信しない（GitHub API 以外）
- GHE Pages（`pages.<host>` や `<host>/pages/`）では localStorage への保存を許さない。同じ GHE のすべての Pages サイトが同じ origin になり、別のサイトのスクリプトが localStorage を読めるため。以前の保存が残っていたら起動時に消す
- sessionStorage はタブごとに分かれるので、別のタブで開いた他の Pages からは読めない。同じタブのまま他の Pages に移動した場合は読まれるので、アプリのリンクは新しいタブで `noopener` で開く
- タブを開き直したときの入力の手間は、入力欄をブラウザのパスワード保存に対応させて減らす（アプリ自身は保存しない）
- 推奨権限
  - fine-grained PAT: Resource owner をリポジトリの owner にし、対象リポジトリに対して Discussions (read/write)、Issues (read/write)、Metadata (read)。1 つのトークンで扱えるのは 1 つの owner の配下だけ
  - classic PAT: `repo`（private / internal リポジトリを扱う場合）
- GHES で fine-grained PAT が使えるかは環境ごとに確認する。使えない場合は classic を案内する

### 将来の認証（v2 以降の検討）
OAuth / GitHub App によるログインはブラウザだけでは完結しない（トークン交換にサーバーが必要）。
必要になったら、小さな認証用プロキシを別コンポーネントとして追加する。v1 では入れない。

## 4. データモデル

すべて GitHub 上のオブジェクトにマッピングする。アプリ固有の情報は Markdown 内の HTML コメントに埋め込む（GitHub 上では表示されない）。

| アプリの概念 | GitHub 上の実体 |
|---|---|
| ワークスペース | アイディア用リポジトリ |
| プロジェクト / テーマ | Discussion カテゴリ |
| ノート | Discussion |
| アウトライン | Discussion 本文（入れ子の Markdown リスト） |
| 行 | リスト項目（行 ID を HTML コメントで付与） |
| 行への議論 | Discussion のコメント（対象の行 ID を埋め込む） |
| 昇格したアイディア | 任意リポジトリの Issue |

### 4.1 ノート本文のフォーマット

```markdown
<!-- idea-outliner:v1 {"defaultRepo":"team-a/web"} -->

- 初回ログイン後の体験 <!-- id:k3f9 -->
  - [ ] チュートリアルを3ステップに短縮 team-a/web#118 <!-- id:p2a1 -->
    - [ ] スキップボタンを常時表示 team-a/web#121 <!-- id:x8d0 -->
    - [ ] 進捗バーを表示する <!-- id:m4c7 -->
  - サンプルデータを最初から入れておく <!-- id:q1z5 -->
- 管理者向け <!-- id:a9b2 -->
  - [x] SSO 設定ガイドを書く team-a/api#97 <!-- id:t6e3 -->
```

ルール:
- 1 行目にメタデータコメント（フォーマットのバージョン、ノート単位の設定）
- インデントは半角スペース 2 つで 1 段
- 各行の末尾に `<!-- id:xxxx -->`。ID はノート内で一意な短いランダム文字列。行の並べ替えや文言変更でも ID は変わらない
- TODO 行は `- [ ]` / `- [x]`。ただの箇条書き行は `- `
- Issue 化した行は本文中に `owner/repo#番号` を含める。GitHub 上ではリンクとして表示される
- 折りたたみ状態などの見た目の情報は本文に保存しない（各ユーザーのブラウザに保存）

パーサーは「アプリが書いたものではない Markdown」（GitHub 画面で手編集された本文）も壊さずに読めること。
ID がない行には読み込み時に ID を振り、次回保存時に書き込む。リストでない段落は「メモブロック」として保持し、そのまま書き戻す。

### 4.2 行へのコメント

Discussion のコメント本文の先頭に対象行を記録する。

```markdown
<!-- idea-outliner:ref id:q1z5 -->
> サンプルデータを最初から入れておく

空の状態だと何をすればいいか分からない、という声は多いので賛成です。
```

- 引用部分は GitHub 画面で読む人のため（どの行への話か分かるように）
- アプリは `ref id` で行と紐づけ、行の横にコメント数を出す
- 行が削除された場合は「削除された行へのコメント」としてまとめて表示する
- `ref` のないコメント（GitHub の画面から書かれたもの）は「ノート全体へのコメント」として表示する。返信はスレッドの下に表示する
- ID がまだ本文に書かれていない行には、投稿の前に保存して ID を書き込む。読み込みのたびに別の ID になり、紐づけが切れるため。保存できないときは投稿しない

### 4.3 Issue 化

「Issue にする」を実行すると:

1. 行き先リポジトリを選ぶ（初期値はノートの `defaultRepo`、なければ前回使ったもの）
2. Issue を作成
   - タイトル: 行のテキスト
   - 本文: 子項目の一覧と、元ノートへのリンク（`<!-- idea-outliner:source ... -->` も埋め込む）
   - ラベル: 任意（行き先リポジトリのラベルから選ぶ）
3. アウトラインの親行がすでに Issue なら、サブイシューとして紐づける
   - 同じリポジトリでも別リポジトリでも、まずサブイシュー API を試す。環境によって使えない場合があるので（§9 #3・#4）、失敗したら本文に「親: owner/repo#番号」と書くだけにする
4. 行に `owner/repo#番号` を追記してノートを保存

順序: Issue を作る前にノートを保存し、衝突や通信エラーがない状態にする。作った後で行に追記できないと、どの行からも辿れない Issue が残るため。
Issue の作成に成功した後の手順（サブイシューの紐づけなど）が失敗しても、Issue は作り直さず、行への追記まで進める。

Issue の状態（Open / Closed）はノート表示時に GraphQL でまとめて取得してチップに反映する。
Issue が Closed になったら行のチェックを付けた見た目にするが、本文の `[ ]` / `[x]` は自動では書き換えない（表示上の扱いのみ）。

## 5. 同時編集の扱い

Discussion 本文の更新には楽観的ロックの仕組みがないため、アプリ側で次のように扱う。

1. 読み込み時に本文を保持（共通の祖先）
2. 保存直前に最新の本文を取得
3. 読み込み時の本文と同じならそのまま保存
   - `updatedAt` は使わない。コメントの追加でも変わるうえ（M0 で確認）、秒単位なので同じ秒の更新を見逃す。本文は同じ問い合わせで取れるので、本文そのものを比べる
4. 違っていれば、行 ID 単位で 3-way マージ（共通の祖先 = 読み込み時の本文）
   - GitHub 上の本文を土台にし、自分の変更（祖先との差分）を当てる。自分が触っていない行は手編集の書式のまま残る
   - 別々の行の変更は自動でマージ
   - 同じ行を両方が変えていたら、その行だけ衝突として表示し、ユーザーに選ばせる。片方が削除し、もう片方が編集した場合も衝突とする
   - 親が削除された行にもう一方が子を足していたら、子は消さず、残っている祖先の下に移す
   - 行の位置（親・順序）は衝突にしない。両方が動かしていたら自分の位置を優先する
   - ID のない行（手編集）は、テキストが同じ行どうしを同じ行として扱う。すでに GitHub に書かれている ID があればそちらに揃える（コメントの紐づけを保つため）
5. 保存は自動（入力が止まって数秒後）＋手動保存
   - ノートを開いただけでは保存しない（ID の付与だけで書き込まない）。ID は最初の編集の保存時に書き込まれる

取得（手順 2）と保存（手順 3）の間に他人が保存する可能性は残るが、チーム利用の頻度では実用上問題にならない想定。v1 ではこれで割り切る。

## 6. 画面

モック: Idea Outliner モック（Claude で作成したデザインキャンバス）

- 上部バー: 接続先・ワークスペース（リポジトリ）切り替え、検索、同期状態
- 左: ノート一覧（カテゴリごと）、新規ノート
- 中央: アウトラインエディタ
  - Enter: 行追加 / Tab, Shift+Tab: インデント / 折りたたみ / チェック
  - 行のメニュー: 「Issue にする」「コメント」「GitHub で開く」
- 右: 議論（行ごとのコメント）、このノートから生まれた Issue の一覧

## 7. 技術選定

| 項目 | 選定 | 理由 |
|---|---|---|
| 言語 | TypeScript | パーサーと API 型を安全に扱うため |
| ビルド | Vite | 静的ファイルとして出力でき、Pages にそのまま置ける |
| UI | Preact | 軽量。アウトラインのような状態の多い UI を素直に書ける |
| API | GraphQL を主に使用、一部 REST | Discussions の作成・更新は GraphQL のみ |
| Markdown 表示 | marked + DOMPurify | コメント表示用。表示前に必ずサニタイズ |
| テスト | Vitest | パーサー・マージ処理を重点的にテスト |
| 配布 | `dist/` を Pages で配信 | GHES の Actions が使えない環境向けに、ビルド済みファイルを手で置く手順も用意 |

依存は最小限にする。外部 CDN から読み込まない（社内ネットワークで動かすため、すべて同梱）。

## 8. セキュリティ

- トークンは既定でタブの間だけ保持する（sessionStorage）。localStorage への保存はユーザーが選んだときだけで、共有 origin では保存しない（§3）。ログ・エラーレポート・URL に絶対に含めない
- 通信先は設定された GitHub / GHES の API のみ。CSP で他のドメインへの接続を禁止する
- Discussion・コメント・Issue の本文はすべて他人が書いた入力として扱い、表示前にサニタイズする
- 「トークンを削除」ボタンを設定画面に置く
- 配布物に既定の接続先以外の情報（社内ホスト名など）を含めない。社内向け設定はビルド時の設定ファイルで差し込む

## 9. 実装前に確認すること（スパイク）

| # | 確認内容 | 確認方法 | ダメだった場合 |
|---|---|---|---|
| 1 | 社内 GHE の Pages からブラウザで API を呼べるか（CORS） | Pages 上の検証ページから `viewer { login }` を GraphQL で取得 | 管理者に相談、またはローカルで開く HTML 版を案内 |
| 2 | GHES 3.20 で Discussions の GraphQL（作成・更新・コメント）が使えるか | 検証ページから実行 | 不可ならノートの保存先を「リポジトリ内の Markdown ファイル」に切り替える案を再検討 |
| 3 | サブイシューの GraphQL / REST が GHES で使えるか | 同一リポジトリで紐づけを試す | 本文リンク方式にフォールバック |
| 4 | リポジトリをまたいだサブイシューが使えるか | GHE 画面で別リポジトリの Issue を「Add sub-issue」 | 同一リポジトリのみサブイシュー化 |
| 5 | GHES で fine-grained PAT が使えるか | 設定画面で発行を試す | classic PAT を案内 |
| 6 | GHE Pages の公開範囲（社内限定にできるか） | GHE 管理者に確認 | 公開範囲が広すぎる場合はアプリを置く場所を再検討（アプリ自体にデータはないので大きな問題ではない） |

## 10. マイルストーン

### M0: スパイク
§9 の確認用に、トークンを入れて API を叩くだけの検証ページを作る。
使い方は `docs/spike/README.md`、結果は `docs/spike/M0-results.md` に記録する。

### M1: 読むだけ
- 接続設定、トークン入力
- ワークスペース（リポジトリ）選択、カテゴリ別ノート一覧
- ノート本文をアウトラインとして表示（パーサー完成）
- Issue チップの状態表示

M1 での決めごと:
- 画面の場所は URL のハッシュ `#/<host>/<owner>/<repo>/<番号>` で表す（トークンは含めない）。同じホストを使う人どうしでリンクを共有できる
- 上部バーの検索は後回しにし、ノート一覧のタイトル絞り込みだけ入れた
- ワークスペースの候補は、自分が関わるリポジトリ（組織のものを含む）に加え、入力された owner の配下も探す。組織のメンバーでなくても見られる internal のリポジトリは、前者には出ないため
- パーサーは改行コード（LF / CRLF）を覚えておき、書き戻すときに合わせる。行末の空白も保持する（ID を足すときは ID コメントの後ろに残す）
- CSP はビルド時に埋め込む。接続先がユーザー入力なので `connect-src` は https 全体に留め、M5 のビルド時設定で既定の接続先に絞る

### M2: 書く
- アウトライン編集（追加・削除・インデント・並べ替え・チェック）
- 保存、同時編集の検知とマージ
- 新規ノート作成

M2 での決めごと:
- 編集中の行だけ入力欄にし、それ以外は Markdown を表示する。リストの書式に合わせられない行（親の本文の桁が 2 でない場合など）は、親の桁に合わせて書き出す
- 行の削除は子孫ごと。子がある行は確認を出す
- アウトデントは、後ろの兄弟を巻き込まないよう親の子孫の後ろに移す
- 権限がないノート（`viewerCanUpdate` が false）は読み取り専用で開く
- 未保存の変更はノートを移動しても保持し、タブを閉じるときは確認を出す。ブラウザを閉じると失われる（localStorage には本文を保存しない）
- やっていないこと: 取り消し（Undo）、ドラッグでの並べ替え、ノートのタイトル変更

### M3: Issue 化
- 「Issue にする」ダイアログ、行き先リポジトリ選択
- サブイシュー連携（スパイク結果に応じて）
- このノートから生まれた Issue の一覧

M3 での決めごと:
- 「このノートから生まれた Issue」は、本文に書かれた `owner/repo#番号` から求める。行から参照を消すと一覧からも消える
- サブイシューにするのは直接の親の行が Issue のときだけ（祖先はたどらない）
- すでに `owner/repo#番号` を含む行には「Issue にする」を出さない
- Issue の本文に、項目の続きの段落は含めない（子項目と元ノートへのリンクのみ）

### M4: 議論
- 行ごとのコメント表示・投稿
- 削除された行へのコメントの扱い

M4 での決めごと:
- アプリから投稿できるのは行へのコメントのみ。返信とノート全体へのコメントは表示だけで、投稿は GitHub の画面で行う
- コメントの編集・削除は GitHub の画面で行う
- 非表示（minimized）にされたコメントは本文を出さない

補足: 悪意ある本文を描画すると、ブラウザのコンソールに CSP（script-src-attr）のエラーが出ることがある。DOMPurify が表示されない文書で解析する時点の報告で、実際の画面には入らず、実行もされない。

### M5: 配布
- ビルド時設定（既定の接続先）
- Pages へのデプロイ手順（Actions 版と手動版）
- README・ライセンス・利用者向けセットアップガイド

M5 での決めごと:
- 既定の接続先は `idea-outliner.config.json`（Git の管理外）か環境変数で渡す。GHES を既定にしたビルドは接続先を固定し、CSP の `connect-src` と `img-src` をそのホストに絞る
- 公開版は接続先をユーザーが入力するので、`connect-src` は https 全体のままにする
- M0 の検証ページは配布物に含めない（`npm run build:spike` のときだけ）
- 同梱ライブラリのライセンス全文を `THIRD_PARTY_LICENSES.txt` として成果物に含める
